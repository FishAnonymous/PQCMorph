# Experiment reproduction

## Scope and correspondence

This implementation was reconstructed from the anonymous 20-page PQCMorph manuscript. It is not a recovered copy of the original prototype. All bundled observations were generated by the supplied implementation against real OpenSSL processes or native EVP calls. Paper-reported values are comparisons, never substituted for missing measurements.

| Paper | Executable reconstruction | Important qualification |
|---|---|---|
| §4.2, Table 3 | `src/pqcmorph.py`, K1–K6; 3 algorithms × 40 trials × 6 relations | Same relation definitions and trial counts; different patch version and host |
| §4.3, Table 4 | Four profiles × four profiles × three repetitions | Real fresh-process TLS 1.3 handshakes, group and protocol parsed from transcripts |
| §4.3, Table 5 | Version mismatch, no common group, abrupt close, unknown group | Five-second per-process deadline; timeout or crash is a failed test |
| Table 6 | `src/faults.py`, ten families × six variants, paired unmodified controls | Variant details and exact baseline were absent; reconstructed operators are new |
| Table 7 | `src/evp_bench.c`, 8 repetitions × 2,000 operations | Reused EVP contexts; no explicit warm-up; allocation/free included in KeyGen |
| §6.4 total cost | Core time plus separately measured native time | Compiler/report/fault campaign excluded; timing cannot recover the original 14.2 seconds |

The original reports 60/60 mutants distinguished. Here the paper-defined core distinguishes 54/60 and the explicitly extended suite distinguishes 60/60. See `FAULTS.md` for the serialization observability issue. Matching numbers in other rows do not make these the original mutants.

## Run individual phases

```bash
# Manuscript-sized KEM/TLS/negative-path workload plus reconstructed mutants
python src/pqcmorph.py --out runs/core --faults

# Full native benchmark; OPENSSL selects the matching default prefix
python scripts/benchmark.py --out runs/native.csv

# Recompute observations and statistics, then render plots if plotting packages exist
python scripts/report.py --input runs/core --native runs/native.csv --out runs/report

# Audit one run without executing OpenSSL
python scripts/audit.py runs/core
```

Output locations must be new. A failure returns a nonzero status. Partial output is retained for diagnosis; it is not a completed result. No command restores historical experiments or invokes an external service.

## Additional measured checks

The following are extensions to the paper workload, stored separately:

- `reference/version-3.6/`: OpenSSL 3.6.4, seed 2027, 720 KEM checks, 48 matrix trials, four negative paths. This is a behavioral compatibility check, not a cross-version performance study.
- `reference/scale-4x/`: OpenSSL 3.5.7, seed 2028, 160 KEM trials per parameter set and 12 TLS repetitions: 2,880 KEM checks, 192 matrix trials, four negative paths. The endpoint-profile space is unchanged; only the repetition budget increases.

To repeat these with existing installations:

```bash
OPENSSL=/path/to/openssl-3.6/bin/openssl python src/pqcmorph.py \
  --out runs/version-3.6 --seed 2027
python src/pqcmorph.py --out runs/scale-4x \
  --kem-trials 160 --tls-trials 12 --seed 2028
```

Only bit-flip positions use the supplied seed. Cryptographic keys, secrets and ephemeral ports use runtime randomness and cannot be reproduced byte for byte. The artifact records all generated material needed to audit the included runs.

## Observation and oracle design

- Key pairs are generated independently for each ML-KEM parameter set. Forty trials reuse the pair while generating fresh encapsulations; key serialization is exercised by separate PEM → DER → PEM subprocesses.
- K2 and K3 accept either a separated 32-byte secret or explicit rejection with no secret; a crash, timeout or reference-source failure cannot satisfy them. The observed ML-KEM implicit rejection emits a different 32-byte secret.
- K5 follows the paper's pair inequality `(ciphertext, secret)`, rather than asserting that both components must individually differ.
- K6 requires nonzero exit status and zero output bytes after a one-byte truncation. An empty file is not a shared secret.
- The TLS client verifies the generated local certificate and hostname. Each handshake gets a new server. Success requires zero status, an established-connection marker, TLS 1.3, and a negotiated group in the intended intersection. Classical output uses `Peer Temp Key`; PQ output may use `Negotiated TLS1.3 group`.
- T2 and T3 are explicitly evaluated over source/follow-up matrix cells. T4–T6 are exercised by dedicated negative scenarios. Failed server startup or connection refusal is an infrastructure failure, not evidence of correct rejection.
- TLS latency in Table 5 covers the client subprocess. Complete core runtime includes server startup/cleanup, certificate generation and evidence I/O. The negative peer accepts the connection, reads a byte and closes; it is not a complete packet-level fault model.

## Native benchmark

The compiler is invoked with `-O2 -std=c11 -Wall -Wextra -Werror`. The benchmark reports the linked OpenSSL version and checks the recovered shared secret before and after each repetition. Each repetition records average latency per operation; reported standard deviations are **sample** standard deviations across repetitions, not individual-operation confidence intervals.

Key generation reuses its EVP context and includes new key allocation/free. Encapsulation reuses an EVP context and includes random generation. Decapsulation reuses the final valid ciphertext from the preceding encapsulation loop. Context creation, compiler time and CSV parsing are outside the operation timers. The lost original benchmark's precise context allocation, warm-up, key reuse and timer choices are not recoverable from the manuscript.

CPU affinity and frequency were not controlled. WSL and other host workloads can affect latency. No claim of an algorithmic speedup or exact reproduction of paper timings is made.

## Evidence files

Each run includes `results.json`, `commands.jsonl` and `material/`. Results contain source/follow-up outputs, sizes, SHA-256 values, command identifiers, return codes and timings. Material includes generated ciphertexts, PEM/DER keys, local test certificates and server logs. **All included keys and secrets are artificial test fixtures; never use them for deployment.** A fresh run generates fresh certificates, so reference certificate expiry does not affect reproduction.

The offline audit cross-checks embedded byte observations against the saved files and command log, replays transformations, recomputes relation verdicts, checks trial coverage, and verifies controls. It shares the executable oracle definitions with the runner; unit tests exercise their semantic boundaries separately. This is consistency checking, not an independent cryptographic proof. `MANIFEST.json` additionally detects changes to distributed files.

The top-level report is regenerated from the primary run only. Additional runs must not be pooled into its sample size. Native samples and metadata are in `reference/native.csv` and `reference/native.json`.
